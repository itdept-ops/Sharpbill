Architecture and control boundaries

The application is a single-organization access-control console: a React SPA uses same-origin HTTP/WebSocket routes to FastAPI; FastAPI verifies provider tokens, issues its own cookie session, evaluates database-backed RBAC, and writes to MySQL. The main risks sit at the seams.

Identity providersGoogle is wired with a DB nonce. Microsoft verification exists, but the browser path and CSP do not.
→
React SPAVite in development; Nginx in production. Strict TypeScript, browser cookie session, WebSocket presence.
→
FastAPI serviceOIDC verification, JWT/session rows, RBAC, settings, logs, presence. Production starts two isolated workers.
→
MySQL 8.012 linear migrations, global roles/settings, no tenant key, no production backup/restore implementation.

Trust boundary strengths

  • Provider tokens are verified server-side; app tokens stay in HttpOnly cookies.
  • Authorization is recalculated from current database permissions on every API request.
  • Mutation DTOs generally reject unknown fields; LIKE and CSV formula inputs are escaped.
  • WebSocket origin, session status, and permissions are periodically revalidated.

Trust boundary failures

  • Current dev bypass is reachable on all host interfaces and can select the admin role.
  • Google organization admission uses email suffix rather than the signed hosted-domain claim.
  • Proxy IP resolution happens after rate limiting; workers do not share limits or presence state.
  • Request logs are not durable, attributable security/audit events.

HighKF-H01 · Active dev-auth is published on every host interface

Verified evidence

  • Runtime advertises dev:true; anonymous role enumeration includes admin.
  • docker-compose.yml:33-34,59-60 publishes API and web as 0.0.0.0/[::].
  • backend/app/routers/dev_auth.py:21-29 accepts arbitrary email/role without authentication; service.py:164-203 can also change an existing user’s role and approval.

Impact

Any party that can reach ports 8010/5174 can mint an administrator session or impersonate/modify an account. Production defaults are safe; the current explicit local configuration is not.

Required remediation

Bind API/web host ports to 127.0.0.1, put dev auth in an explicit Compose profile, require a developer secret or loopback source backstop, and remove arbitrary role selection from any network-reachable bypass.

Close when

An off-host probe cannot reach either port; a regression test proves dev auth never mounts outside the isolated profile and cannot assign admin without the backstop.

HighKF-H02 · Microsoft sign-in and provider failover are not operational

Verified evidence

  • LoginPage.tsx:42-92,121-142 renders only Google; the dormant msal.ts:21-28 neither fetches the server nonce nor posts its token.
  • microsoft.py:52-55 requires the DB-issued nonce. nginx.conf:15 allowlists Google endpoints only.
  • auth.py:39-47 reports configured client IDs, not effective site toggles; settings.py:55-62 permits Microsoft-only even if Azure is unconfigured.

Impact

A supported settings state (Google=false, Microsoft=true) locks every browser user out. The public site advertises a flow that cannot complete.

Required remediation

Return configured AND enabled provider state, implement a provider-supported nonce/state flow and Microsoft UI, post the token, update CSP, and add controlled break-glass recovery. Prefer an authorization-code + PKCE/BFF design for the final enterprise flow.

Close when

Google-only, Microsoft-only, dual-provider, provider-outage, and toggle/failover E2E scenarios all pass in the production image.

HighKF-H03 · Enterprise admission control fails open and checks the wrong Google claim

Verified evidence

  • Current runtime is signup_mode=open, Google enabled, with no allowed Google domains; any verified Google account can provision a standard user.
  • config.py:28-31 and service.py:58-67,112-124 define empty allowlists as allow-all.
  • When a domain is configured, service.py:60-63 checks the email suffix; google.py:51-56 discards Google’s signed hd claim.

Impact

Current onboarding is broader than an enterprise directory. A matching email suffix is not proof of Workspace organization membership, so the intended domain restriction is not authoritative.

Required remediation

Default enterprise deployments to approval/closed, require explicit public-signup acknowledgement, validate the exact signed hd claim, persist organization context, and integrate authoritative group/SCIM policy where required. See Google’s OIDC claim reference.

Close when

Tests reject a verified matching-email-domain account without the required hd, and production startup fails without an explicit admission policy.

HighKF-H04 · Unauthenticated nonce issuance enables database amplification

Verified evidence

  • auth.py:50-54 exposes state-changing GET /api/auth/nonce.
  • nonce.py:26-50 inserts/commits per request; expired rows prune only during consume.
  • request_logging.py:20-30 skips the endpoint; it receives the loose 600/minute per-process bucket. Live read-only inspection found expired residue.

Impact

Cross-origin loads or scripted callers can grow shared storage, exhaust the general API bucket, and make the next legitimate consume perform an oversized delete.

Required remediation

Use POST, Cache-Control: no-store, a tight distributed limiter, per-client/outstanding caps, bounded scheduled TTL deletion, and observability for issue/consume ratios.

Close when

Load tests demonstrate bounded rows and cleanup work under abuse, and issuance is separately rate-limited and auditable across all workers.

HighKF-H05 · Production topology breaks rate limiting and live presence

Verified evidence

  • Middleware reconstruction proved main.py:26-31,83-109 executes rate limiting before trusted proxy headers rewrite the client address; proxied users share the proxy socket bucket.
  • backend/Dockerfile:27-31 documents process-local limits/presence, then starts two workers.
  • ratelimit.py:1-29 and ws.py:40-50,84-101 hold module-local state.

Impact

Behind Caddy, one user can exhaust the shared proxy bucket; across workers, attackers get independent buckets while rosters, caps, and broadcasts split unpredictably.

Required remediation

Resolve trusted client IP at the server/edge before app middleware, enforce edge/Redis limits, use shared presence/pub-sub, and run one worker until coordination is externalized. FastAPI notes that workers do not share memory.

Close when

A proxy-topology test identifies distinct clients safely, multi-instance load tests enforce one global policy, and presence convergence meets a stated SLO.

HighKF-H06 · The test harness can erase any configured database

Verified evidence

  • backend/tests/conftest.py:14-22 trusts arbitrary TEST_DATABASE_URL without asserting it differs from the main URL or has a test-only name.
  • The autouse fixture at conftest.py:68-105 deletes data from every application table before every test.

Impact

A mistyped or injected URL can turn a routine pytest invocation into destructive production-data loss.

Required remediation

Create a random ephemeral database, assert strict test naming plus inequality to every non-test URL and environment, deny non-local hosts/accounts, and require a second explicit destructive-test acknowledgment.

Close when

Tests deliberately pointed at the main/prod URL abort before opening a transaction or issuing DDL/DML, and CI provisions/disposes an isolated database.

HighKF-H07 · MySQL 8.0 is past end of life

Verified evidence

  • Live server reports 8.0.46; docker-compose.yml:5-6 and ci.yml:13-20 pin MySQL 8.0.
  • Oracle identifies 8.0.46 as the final 8.0 release and April 2026 as EOL, recommending 8.4 LTS in the official release notes.

Impact

The database baseline no longer receives normal community maintenance and cannot be approved as a new enterprise platform.

Required remediation

Move development and CI to an exact MySQL 8.4 LTS patch/digest, run Upgrade Checker, rehearse upgrade and rollback-by-restore on a clone, and validate all migrations, collations, query plans, and backups.

Close when

8.4 LTS is the tested baseline and a timed restore/rollback rehearsal meets approved RPO/RTO. Do not repoint the current volume blindly.

HighKF-H08 · OIDC subjects and nonces compare case-insensitively

Verified evidence

  • user_identity.py:11-25 and login_nonce.py:8-26 inherit utf8mb4_0900_ai_ci.
  • Live DDL and a read-only comparison confirmed mixed-case strings compare equal. Lookups/unique keys therefore normalize standards-distinct values.
  • OIDC defines sub and nonce as case-sensitive; MySQL documents the chosen collation as case-insensitive. See OIDC Core and MySQL comparison rules.

Impact

A case-modified nonce can satisfy equality, and standards-distinct provider subjects can collide. Current Google/Microsoft identifiers reduce practical collision likelihood but do not make the schema contract correct.

Required remediation

Migrate opaque values to VARBINARY, ASCII binary, or explicit binary/case-sensitive column collations; preserve canonical issuer/tenant context.

Close when

Real-MySQL tests prove AbC != abc for both uniqueness and consume queries, including forward/backward migration verification.

HighKF-H09 · Concurrent settings updates can disable every provider

Verified evidence

  • settings.py:41-66 performs an unlocked singleton read, validates each request’s in-memory merged state, then commits only supplied columns.
  • site_settings.py:22-30 has no database constraint; live metadata confirms zero CHECK constraints.

Impact

Two transactions can each disable one currently-enabled provider, both validate successfully, and leave Google=false/Microsoft=false after existing sessions expire.

Required remediation

Lock the singleton row with SELECT … FOR UPDATE, validate effective/configured providers inside the lock, and add an enforced database CHECK preserving at least one enabled provider.

Close when

A two-connection race test cannot reach a zero-provider state and the constraint rejects direct SQL that violates the invariant.

HighKF-H10 · Production database TLS is optional and migrations bypass connection policy

Verified evidence

  • config.py:12-15,52-56 rejects insecure production cookies but allows DB_REQUIRE_TLS=false.
  • db.py:8-24 applies verified TLS/UTC only to app connections; alembic/env.py:31-43 creates a separate engine without either policy.

Impact

Production can start with plaintext database transport. A TLS-required database can also reject Alembic, or migrations can use different security/time semantics from runtime writes.

Required remediation

Fail production startup unless verified DB TLS is on, enforce require_secure_transport server-side, share one connection factory/policy between app and Alembic, use separate runtime/migrator principals, and verify the negotiated cipher.

Close when

Negative tests reject plaintext and bad CA/hostname connections for both runtime and migrations; readiness reports secure transport without leaking details.

HighKF-H11 · Request logs are not an enterprise audit trail

Verified evidence

  • request_log.py:15-30 stores only method/path/user/IP/status/time; no action, target, before/after, reason, request/trace ID, actor snapshot, provider, or event version.
  • request_logging.py:47-95 is best-effort and mutable; live aggregation found all 15 successful Google login rows unattributed.
  • Product copy claims “AUDIT-READY” and provider identity in the trail, but LandingPage.tsx:12 exceeds what the data records.

Impact

Security incidents, privileged changes, access reviews, and compliance evidence cannot be reconstructed reliably; login attribution may be null or identify the old cookie principal.

Required remediation

Define structured immutable security events; capture when/where/who/what/outcome, actor/target, provider/tenant, correlation ID and before/after summary; write via transactional outbox and ship to restricted append-only/SIEM storage. Follow OWASP logging guidance.

Close when

Authentication and every privileged mutation produce attributable, versioned, tamper-monitored events and loss/lag alerts under failure injection.

HighKF-H12 · Production database, migration, HA, backup, and restore controls are not implemented

Verified evidence

  • deploy/docker-compose.prod.yml:1-37 is reference-only, has no database or migration job, and is not connected to CI/CD.
  • health.py:11-18 combines liveness/readiness and checks only SELECT 1, not Alembic revision.
  • Repository search found no IaC, PITR/snapshot policy, restore test, RPO/RTO, Multi-AZ, migration lock, secrets rotation, or rollback automation.

Impact

There is no reproducible evidence that production data survives operator error, engine failure, regional loss, or a bad schema change.

Required remediation

Implement IaC-managed MySQL 8.4 LTS/RDS, KMS encryption, private networking, Multi-AZ, PITR, cross-account/region protection as required, Secrets Manager, separate principals, serial migration job, schema-aware readiness, and quarterly restore drills. See official RDS backup/restore guidance.

Close when

A production-like deployment and destructive restore game day demonstrate approved RPO/RTO, schema gating, rollout, and rollback-by-restore.

MediumKF-M01 · The special admin role is assignable through ordinary subset rules

Evidence and impact

users.py:45-63,206-234,310-330 treats the literal admin role as a meta-privilege but lets a non-admin holding the same permission set assign it. settings.py:43-54 can also choose admin as the public default. This grants hierarchy/system-role bypasses not represented by permission keys.

Remediation / acceptance

Require an actual admin or explicit admin.assign capability; forbid admin/system/high-privilege onboarding defaults. Add custom-all-permissions negative tests for single, bulk, and settings paths.

MediumKF-M02 · Delegated admin-target protections are inconsistent

Evidence and impact

Full kick guards self/admin targets at users.py:401-413; individual revocation at :441-454 discards the actor and does not load/guard the target. Direct-permission replacement at :337-364 can strip an admin’s direct grants. This is administrator-device denial of service and policy damage, not loss of built-in admin role grants.

Remediation / acceptance

Centralize target hierarchy policy and apply it to every session, permission, role, status, and bulk mutation. Add a table-driven delegated-actor × target-role regression suite.

MediumKF-M03 · SameSite is treated as the complete mutation CSRF defense

Evidence and impact

main.py:35-57 guards only two login routes; jwt.py:35-54 relies on SameSite=Lax. Same-site sibling origins still send the cookie, and no-body POSTs such as approve/kick/heartbeat accept form submissions. A runtime sibling-origin form probe reached authentication. Risk is material wherever sibling subdomains are not equally trusted.

Remediation / acceptance

Validate same-origin Origin/Referer or Fetch Metadata with fallback on every unsafe method, or require a session-bound CSRF/custom header; consider SameSite=Strict and __Host-session. Test hostile cross-site and same-site sibling origins. See OWASP CSRF guidance.

MediumKF-M04 · Sessions and identity-adjacent data lack a lifecycle policy

Evidence and impact

user_session.py:25-34 has no expires_at; listings filter only revocation, and live data had 10 rows older than the 8-hour token TTL still labeled active. There is no session cap/purge. Provider/allowlist changes affect only new logins. GPS, IP, user agent, provider subject, and revoked-session retention/deletion are not governed.

Remediation / acceptance

Persist token expiry, enforce idle/concurrent-session limits, revoke on provider policy when intended, run bounded cleanup, and approve data-purpose/retention/deletion schedules with user/admin workflows. Prove expired rows disappear from active APIs and deletion jobs meet SLOs.

MediumKF-M05 · Public API inputs lack size and finite-number limits

Evidence and impact

schemas/auth.py:8-10 accepts arbitrarily large tokens; a 10,000,000-character value validated. deploy/Caddyfile:1-11 has no body cap. LocationUpdate.accuracy accepts positive infinity. Oversized unauthenticated bodies consume workers/memory and non-finite values can poison persistence/analytics.

Remediation / acceptance

Set edge and ASGI body limits, conservative JWT length limits, finite-only geospatial validation with realistic maxima, and request timeouts. Add boundary/fuzz tests and verify oversized requests are rejected before provider/network/DB work.

MediumKF-M06 · Error contracts and provider-outage handling are inconsistent

Evidence and impact

errors.py:1-4,26-50 promises a uniform envelope but does not handle Starlette HTTP exceptions; live 404/405 responses use default {detail}. Google/Microsoft network/JWKS failures collapse into 401 invalid-token responses. Clients cannot distinguish invalid credentials, unavailable upstreams, routing errors, and retryable failures.

Remediation / acceptance

Define/version one error schema, register HTTPException handling, map provider transport failures to bounded 503 responses, add explicit timeouts/retry/circuit metrics, and contract-test every status family without reflecting tokens.

MediumKF-M07 · Request logging adds a second database transaction to responses

Evidence and impact

main.py:60-80 waits for a threadpool logging call; request_logging.py:70-95 opens and commits another DB session. It fails open, omits rate-limited traffic, and prefix skips can hide future paths. Under load or DB degradation this adds latency, connection pressure, or silent evidence loss.

Remediation / acceptance

Separate access logs from transactional security events; use a bounded queue/outbox and centralized structured logging with loss/backpressure metrics. Performance tests should show request latency and pool health remain within SLO during sink slowdown/failure.

MediumKF-M08 · Migration drift, historical seeds, and rollout safety need repair

Evidence and impact

alembic current/heads both return 0012, but alembic check produces seven false timestamp-default diffs because MySQL normalizes CURRENT_TIMESTAMP(6) to now(6). Historical migrations seed/delete fixed surrogate IDs; migration 0006 drops data and cannot restore it. CI tests only fresh upgrade, not populated N-1/N-2 or zero-downtime behavior.

Remediation / acceptance

Normalize equivalent defaults in the comparator; resolve seeds by natural key; adopt expand/contract DDL, metadata-lock/capacity preflight, backup gates and restore rollback. Add drift plus populated snapshot upgrade tests to CI.

MediumKF-M09 · Security and business invariants exist only in application code

Evidence and impact

Live schema has no CHECK constraints. Provider availability, signup_mode, boolean domains, latitude/longitude/accuracy bounds, and the singleton settings row are not enforced by MySQL. Alternate writers, migrations, races, or bugs can persist states the API rejects.

Remediation / acceptance

Add focused DB constraints for durable security/business invariants—not every presentation rule—and make settings singleton non-auto-increment/guarded. Test both ORM and direct-SQL rejection on MySQL 8.4.

MediumKF-M10 · Directory, log, role, session, and export queries will not scale

Evidence and impact

Live EXPLAIN confirmed table scans/sorts for common user queries and explicit session sorts. users.py:82-203 uses leading-wildcard LOWER search, offset/count pagination, and a cursor-holding unbounded export. Logs are similar; role listing performs one count per role.

Remediation / acceptance

Use keyset pagination, workload-validated composite indexes, grouped counts, bounded/asynchronous exports, and a deliberate search strategy. Load-test production-like cardinality and enforce query count/latency budgets with EXPLAIN ANALYZE.

MediumKF-M11 · Request-log key and retention mechanics are not durable at scale

Evidence and impact

request_log.py:21 uses signed INT for an append stream (about 249 days at 100 logged requests/s). request_logging.py:13-18,62-93 uses a process-local counter and unbounded delete every 500 inserts; restarts/low traffic can leave old rows indefinitely.

Remediation / acceptance

Migrate to BIGINT, scheduled bounded purge or time partitioning, retention/legal-hold configuration, archive/export strategy, and alerting for keyspace/storage/cleanup lag. Test purge under realistic volume and replicas.

MediumKF-M12 · Connection budgets, timeouts, retries, and timestamp semantics are implicit

Evidence and impact

db.py:18-24 leaves pool size/overflow/checkout and driver read/write/query timeouts at defaults; two workers can open roughly 30 connections before migrations/admin tasks. App code mixes aware and naive UTC, while updated_at server generation is not mapped/refreshed consistently.

Remediation / acceptance

Budget connections from worker/instance count, configure and instrument pool/driver/statement timeouts, retry only safe idempotent work, normalize one UTC representation, and correctly fetch server-generated timestamps. Test failover, deadlock, saturation, and serialization.

MediumKF-M13 · Frontend and backend permission contracts disagree

Evidence and impact

App.tsx:64-70 admits settings.manage, then SettingsPage.tsx:22-29,41-45 calls roles/users/approval APIs requiring three other permissions. Failures become empty lists. Conversely, backend user role/direct-grant APIs need only users.manage while UI additionally requires roles.manage.

Remediation / acceptance

Define one permission-to-capability matrix, split/gate settings panels or align APIs, preserve explicit forbidden errors, and table-test every route, menu, component, and endpoint for representative roles.

MediumKF-M16 · The SPA has no render recovery or client error telemetry

Evidence and impact

App.tsx:24-86 provides Suspense only; repository search found no Error Boundary. Render exceptions or stale lazy chunks can blank the whole SPA. API/WebSocket responses are trusted via TypeScript casts, and many requests have no timeout/cancellation, allowing stale updates without diagnostic context.

Add root and route-level error boundaries, stale-chunk reload/retry UX, sanitized client telemetry with correlation IDs, OpenAPI-generated/runtime-validated critical contracts, and AbortSignal timeouts. React documents boundaries in the official API reference.

MediumKF-M17 · Access-control edits are last-writer-wins and can silently lose changes

Evidence and impact

AdminRolesPage.tsx:32 and UserEditModal.tsx:127 replace complete permission sets from rendered snapshots; rapid or concurrent edits can derive from the same old set and responses can arrive out of order. Server resources lack versions/ETags, mutation idempotency, and a conflict contract.

Remediation / acceptance

Serialize/disable per-resource mutations or provide add/remove operations; add optimistic versions/ETags and conflict UX; define idempotency for retryable operations and an API evolution/versioning policy. Test two-admin and high-latency races.

MediumKF-M18 · Quality gates do not cover the application’s highest-risk behavior

Evidence and impact

Backend breadth is good (137 tests), but there is no coverage floor, mypy/Pyright, warning-as-error, proxy topology, Microsoft verifier, CSRF, test-DB guard, two-worker, or migration-drift gate. Frontend has 3 files/11 tests and 3 desktop Chromium E2E tests—no provider matrix, settings/role builder, mobile, accessibility, error boundary, or presence suite. ESLint omits Hooks and JSX-a11y rules.

Remediation / acceptance

Adopt risk-based coverage ratchets, typing, Hooks/a11y lint, provider/security/concurrency regression suites, mobile/axe projects, mutation and restore scenarios, warning discipline, and test artifacts. Require the suite in protected-branch rules.

MediumKF-M19 · Dependency and build inputs are only partially reproducible and scanned

Evidence and impact

Direct Python packages are pinned, but transitives have no lock/hashes; CI runs pip-audit --no-deps, missing transitive CVEs that the manual full scan covered. Full npm audit reports 5 dev-tool entries (Vitest UI critical is not invoked; Vite is all-interface). Python/Node/base image tags are not digest-pinned; RDS CA is downloaded without content verification. No SBOM/provenance/security scan is enforced for deployable images.

Remediation / acceptance

Use hash-locked Python resolution, full-graph audit, coordinated Vite/Vitest upgrade, digest-pinned builders/runtimes/actions, verified build inputs, SBOM, signed provenance and container policy gates with documented reachability exceptions.

MediumKF-M20 · Operational telemetry, health semantics, and runtime hardening are incomplete

Evidence and impact

There are no structured JSON logs, metrics, traces, correlation IDs, SLOs/alerts, error service, or deployment/runbook ownership. Health conflates liveness and DB readiness and omits schema. Reference containers lack resource limits, read-only filesystems, dropped capabilities/no-new-privileges, web/Caddy healthchecks, and rollout/rollback orchestration. Local API also receives the MySQL root password because the whole root .env is injected.

Remediation / acceptance

Define SLIs/SLOs and on-call alerts; add correlation/trace propagation, separate liveness/readiness/startup checks, least-privilege per-service secrets, container hardening/resource budgets, deployment and rollback automation, synthetic checks, dashboards and runbooks. Prove behavior with failure injection.

LowKF-L01 · Session JWTs have no issuer/audience/type or key-rotation contract

Evidence and impact

jwt.py:11-32 correctly pins HS256 and requires exp/iat/sub/jti, but omits issuer, audience, token type, KID, and a verification keyring. This is defense-in-depth today because tokens are app-internal; it complicates safe secret rotation and future multi-service use.

Remediation / acceptance

Define explicit iss/aud/typ, key IDs and overlapping rotation windows; keep algorithms fixed and add old/new key acceptance/rejection tests plus an operational rotation drill.

LowKF-L02 · Session-row ownership is not reasserted against JWT subject

Evidence and impact

auth/deps.py:45-61 resolves a user from JWT sub and an active session from jti; sessions.py:33-38 does not explicitly assert both belong together. Unique random jti and signed tokens make exploitation unlikely without another failure.

Remediation / acceptance

Query/validate session.user_id == sub atomically and add a mismatched subject/jti negative test so a future token/session refactor cannot weaken the binding.

LowKF-L03 · Identity lifecycle and disclosure can be narrowed

Evidence and impact

Google admin bootstrap uses mutable/reassignable email rather than immutable subject at service.py:39-54; canonical User.email is not refreshed on provider change. schemas/user.py:9-14,75-78 returns stable provider subjects to any directory viewer.

Remediation / acceptance

Use immutable bootstrap IDs or authoritative group/SCIM workflow, define email synchronization/audit behavior, and return identity IDs only to self/admin DTOs. Add reassignment and least-data response tests.

LowKF-L04 · Session/cache/edge hardening and privileged step-up are incomplete

Evidence and impact

Auth/session/PII responses have no explicit Cache-Control: no-store; the cookie is host-only but not __Host- prefixed. The reference edge has no explicit HSTS/security-header policy for API responses. Privileged RBAC, settings, export, and bulk actions require no recent authentication/step-up or IdP assurance signal.

Remediation / acceptance

Add cache directives, __Host-session, HSTS at the TLS edge, consistent API headers, and policy-driven recent-auth/MFA/Conditional Access for high-impact operations; verify with production-response tests.

LowKF-L05 · Third-party script and geolocation UX exceed minimum exposure

Evidence and impact

frontend/index.html:34 loads Google’s remote script on every route even when disabled. LoginPage.tsx:36-39 requests precise location immediately after login without an in-product purpose/retention explanation. Browser consent exists, but privacy exposure and surprise can be reduced.

Remediation / acceptance

Load provider SDKs on demand after effective configuration, add a clear purpose/retention choice before location prompt, persist opt-out, and test that public/non-Google routes make no Google request.

LowKF-L06 · One router mutation is a complexity hotspot

Evidence and impact

Radon rates 172 of 173 Python blocks A-C with average complexity 3.16, a strong result. users.bulk_action:207 is the exception at D / 23 and combines authorization, action branching, per-item transactions, error mapping and response aggregation.

Remediation / acceptance

Extract policy and action services with typed outcomes while preserving intentional partial-success semantics. Bring the function below the agreed complexity threshold and retain branch/transaction tests.

LowKF-L07 · Documentation and public security claims have drifted

Evidence and impact

README.md:140,281 says migrations stop at 0010 although head is 0012; SecurityPage.tsx:169 says nonce binding is not wired although Google now uses it; landing content advertises working Microsoft and an “audit-ready” provider trail that do not exist.

Remediation / acceptance

Generate architecture/API/migration facts where possible, add claim-review ownership to release checklists, and describe current limitations plainly. Documentation tests should fail on migration count/provider capability drift.

DecisionKF-A01 · Declare one tenant per deployment—or redesign every data boundary

Evidence and consequence

Users, roles, permissions, settings, sessions, logs and all queries are global. Microsoft tid is verified transiently but not persisted; identity uniqueness is provider + subject. This is acceptable for a deliberately single-company console, but is a High blocker for shared SaaS.

Decision / acceptance

Single tenant: enforce one organization/tenant at startup and document one isolated database/deployment per customer. Shared SaaS: add organization roots, tenant FKs and composite constraints everywhere, tenant-aware identity keys such as (tid,oid), mandatory scoped repositories, cross-tenant negative tests, tenant audit, and isolation strategy. See Microsoft identity guidance.

Domain conclusions

The register above is the authoritative issue list. These summaries explain the engineering posture behind the scores and keep strengths visible alongside risk.

Python / FastAPI

Verdict: well-structured small service, not yet production-operational.

  • Strong: compact routers/models, low average complexity, Pydantic validation, generic 500s, threadpool treatment for sync ORM work, non-root production user.
  • Strong: provider signature/audience/issuer checks, JWT claim requirements, server-side session revocation and per-request RBAC.
  • Gap: proxy/rate limiter ordering, process-local coordination, destructive test guard, CSRF, input size, uniform errors, typing/coverage/security gates.
  • Recommendation: retain the synchronous SQLAlchemy design for now; invest in service/policy boundaries and production controls before considering framework churn.

Database architecture

Verdict: sound relational kernel for one organization; weak enterprise lifecycle.

  • Strong: InnoDB, utf8mb4, sensible FKs, composite RBAC keys, atomic nonce consume, first-login race recovery, last-admin row locking, UTC app sessions.
  • Gap: EOL MySQL, opaque-ID collation, settings invariant race, TLS split, no CHECK constraints, session/log retention, scale indexes, noisy drift gate.
  • Gap: no implemented managed database, migration orchestration, HA/PITR/restore evidence or schema-aware readiness.
  • Recommendation: upgrade/rehearse 8.4 first, then evolve with expand/contract migrations and evidence-producing recovery automation.

React / TypeScript

Verdict: lean SPA with good foundations and one broken identity capability.

  • Strong: strict TypeScript, no dangerous HTML/eval/session storage, route-level splitting, lean bundle, reduced-motion support, reconnect/fallback behavior.
  • Gap: Microsoft is advertised but unreachable, provider toggles are inconsistent, permission contracts drift, and access edits race.
  • Gap: missing mobile app navigation, 320 px overflow, systemic dialog/form accessibility gaps, no render boundary or client telemetry.
  • Recommendation: fix provider state first; then establish shared accessible primitives, generated contracts, mutation orchestration, and risk-centered tests.

Security / identity

Verdict: good cryptographic verification, incomplete surrounding control plane.

  • Strong: algorithms pinned, nonces DB-backed and atomic, provider errors sanitized, identities normally keyed by immutable subject, sessions revocable.
  • Gap: active dev bypass exposure, open admission, wrong Google organization claim, SameSite-only mutation policy, proxy topology, provider failover.
  • Gap: request logging is not a security event system; no step-up, key rotation runbook, or tenant decision.
  • Recommendation: treat identity as an end-to-end product capability—configuration, UX, admission, sessions, audit, recovery and incident controls—not only token verification.

Supply chain / CI

Verdict: application packages are clean; deployable artifact and governance controls are not.

  • Strong: Python transitive and production npm scans are clean; builds are deterministic enough for local development; last 10 CI runs passed.
  • Gap: Nginx runtime is stale, dev tool advisories exist, Python transitives are unlocked, images/actions are not digest/SHA pinned.
  • Gap: no enforced container scan, SBOM/provenance, signed release, protected environment, or branch/ruleset.
  • Recommendation: make the built digest—not the source tree—the governed release unit.

Operations / resilience

Verdict: reference architecture only.

  • Strong: local Compose is convenient; DB/API health and configurable ports work; source explicitly says deployment is not wired.
  • Gap: no IaC, secret rotation, least-privilege DB roles, resource budgets, telemetry, SLOs, deploy/rollback, HA, PITR, restore drill or incident playbook.
  • Gap: liveness/readiness/schema state are conflated; two-worker image contradicts application state model.
  • Recommendation: build one boring, observable, reproducible production path and game-day it before feature expansion.
