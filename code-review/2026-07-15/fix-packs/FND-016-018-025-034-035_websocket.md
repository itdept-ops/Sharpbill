# Fix Pack — FND-016 / FND-018 / FND-025 / FND-034 / FND-035: WebSocket presence hardening

**Severity:** Medium (FND-016, -018, -025), Low (FND-034, -035) · **Domain:** WebSocket & reliability · **Effort:** M
All live in `backend/app/routers/ws.py` (+ a new `backend/tests/test_ws.py`). Do together.

## Context
`[repository root]`. `backend/app/routers/ws.py` implements `/api/ws/presence`: an in-memory
`PresenceHub` broadcasts who's online. `presence_ws` (:110) authenticates on connect and re-checks every
≤30s. It re-implements the auth pipeline in `_authenticate` (:69). The front-end client is
`frontend/src/presence/PresenceContext.tsx` (HTTP polling fallback exists).

---

## FND-016 — Sync DB queries on the event loop + unthrottled frames
**Evidence:** `presence_ws` is `async` but calls **synchronous** `SessionLocal()` / `db.get` /
`active_session` directly — on connect (`ws.py:112-124`) and every re-auth (`ws.py:136-142`) — with no
`run_in_threadpool`. Each blocks the worker's single event loop. `ws.py:133`
(`await websocket.receive_text()`) has no rate limit, so a client can spam frames to force re-auth churn.

**Fix:** wrap every synchronous DB block in `starlette.concurrency.run_in_threadpool(...)` (the pattern is
already used in `backend/app/main.py:57`), or switch to an async DB path. Add a minimum interval between
re-auths regardless of inbound frame rate (debounce: ignore frames that arrive faster than, say, once/second).

## FND-018 — No connection cap; dead connections leak
**Evidence:** `PresenceHub` (`ws.py:26-64`) appends to an unbounded `self._conns` with no per-user/global
cap; WS upgrades bypass the rate-limit/audit middleware (they aren't `/api`-limited in `main.py:71-89`).
Half-open sockets are pruned only on a failed `send` during `broadcast` (`ws.py:59-63`), so idle dead
connections linger.

**Fix:** enforce a per-user connection cap (e.g. close the oldest when a user exceeds N) and a global cap;
add a periodic ping / idle-timeout reaper that drops silent connections; count WS upgrades against a limiter.

## FND-034 — Origin check, revocation lag, count leak
**Evidence:** `ws.py:110-113` accepts the upgrade with no `Origin`/`Host` validation (cross-site WS hijack
is prevented only by SameSite=Lax). `ws.py:133` re-auth interval `_RECHECK_SECONDS=30` means a
kicked/deactivated user stays connected up to 30s. `ws.py:49-58` broadcasts the online **count** to every
connection, including those lacking `presence.view` (the REST endpoint `presence.py:15` gates the same count).

**Fix:** validate `Origin` against an allowlist on upgrade (reject cross-site); reduce re-auth latency for
revocation (or push a revocation signal); only include `count` for connections with `presence.view`
(mirror the REST gate) — or intentionally document that the bare count is public and align the REST endpoint.

## FND-035 — Roster diverges from the `last_seen` online model
**Evidence:** `PresenceHub._roster` (`ws.py:33-37`) reflects only live WS connections, which diverges from
the `last_seen`-based online model used by REST (`presence.py`, `is_online`), so viewers can under-report
who's online (e.g. a user active via polling isn't in the WS roster).

**Fix:** reconcile the two — either drive the roster from the same `last_seen` source of truth, or document
that the WS roster is "connected via WS now" and label it distinctly in the UI so it isn't mistaken for the
authoritative online set.

## FND-025 — Zero automated tests for this subsystem
**Evidence:** no `test_ws*` exists; `_authenticate` (a re-implemented auth pipeline) and the `can_view`
roster gate are untested.

**Fix:** add `backend/tests/test_ws.py` using FastAPI's `TestClient` websocket support.

## Constraints — do NOT change
- Keep the HTTP polling fallback working (`presence.py` `heartbeat`, `PresenceContext`).
- Keep `_authenticate`'s security checks (decode → active/approved → epoch → session row); don't loosen them.
- Preserve the `{"type":"presence", ...}` message shape the client expects (`PresenceContext.tsx`).

## Acceptance criteria
- New `backend/tests/test_ws.py` proving: unauthenticated upgrade closes with 1008; a revoked/kicked user
  is severed on re-auth; the roster (`online` array) is omitted for a connection lacking `presence.view`;
  a cross-`Origin` upgrade is rejected.
- No synchronous DB call runs on the event loop (code review + the tests don't hang).
- Per-user connection cap enforced (test opening N+1 connections).
- `docker compose exec api pytest` green; `ruff` clean.
