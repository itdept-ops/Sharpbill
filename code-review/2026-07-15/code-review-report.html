Sharpbill — Enterprise Standards Audit

Access-control console · FastAPI + React + MySQL (local Docker) · Review date 2026-07-15 · Review-only, no source modified

Rebranded archival copy: product labels were normalized to Sharpbill for this repository; dates, finding IDs, scores, and evidence boundaries remain those of the 2026-07-15 review.

Scope: entire repository at its current root, excluding deploy/ and all AWS deployment concerns (per instruction). Branch as-checked-out (10 migrations, uncommitted UI-prefs work present).

B−

Overall: a genuinely well-engineered codebase with strong security fundamentals. Every quality gate is green, the auth/RBAC core is careful and hard to fault, and there are no Critical findings and nothing currently exploitable by an anonymous attacker. The audit's value is in the margins: dependency hygiene, a handful of RBAC/reliability edge cases, and operational hardening. The B− reflects real, fixable gaps — not fragility.

Executive summary

  1. One production dependency ships a known High CVE. react-router-dom 6.30.1 carries an open-redirect / XSS advisory (GHSA-2w69-qvjg-hvjx, CVSS 8.0); the fix is a non-breaking bump to 6.30.4. CI has no dependency-audit gate, which is why it (and vulnerable backend packages) went unnoticed. FND-001
  2. The RBAC "who can act on whom" boundary is incomplete. A non-admin delegate holding users.manage or presence.kick can deactivate, demote, and force-logout every admin except the single last one — and the last-admin guard itself is a non-locking check-then-act that two concurrent requests can race to zero admins. FND-002 FND-003
  3. Two config states can lock the whole org out, and neither is guarded: disabling both OAuth providers, or having signup_mode="closed" block the ADMIN_EMAILS bootstrap. Recovery would require direct DB surgery. FND-006 FND-007
  4. The in-memory security state doesn't survive the shipped runtime. Rate-limiting, the token-replay guard, and the presence hub are per-process, yet the prod image runs --workers 2; worse, in the compose topology every API request arrives from the web-proxy container, so per-IP limiting and the audit log's source IP collapse to one value. FND-009 FND-023
  5. Operational + observability hardening is thin: unbounded per-request audit writes with no retention, no security response headers on the SPA, root containers, public API docs, and a WebSocket path that runs sync DB queries on the event loop and has no tests. Individually minor; together they're what turns a routine incident into a bad one. FND-013 FND-016 FND-021

FND-001 HIGH Known-vulnerable production dependency: react-router-dom 6.30.1

Domain
Dependencies & supply chain · OWASP A06:2021 Vulnerable Components
Evidence
frontend/package.json:17 pins react-router-dom 6.30.1. npm audit reports it (and its react-router / @remix-run/router deps) as High: open-redirect / XSS (GHSA-2w69-qvjg-hvjx, CVSS 8.0) plus GHSA-9jcx-v3wj-wh4m and GHSA-2j2x-hqr9-3h42. Why it matters
A shipped production dependency with a live High advisory and a public exploit class. Fix direction
Bump to react-router-dom 6.30.4 (non-breaking, semver-minor) and add an npm audit --audit-level=high gate to CI. See fix-packs/FND-001.

FND-002 MEDIUM A non-admin delegate can disable, demote, and kick every admin but the last

Domain
Security: Authorization / RBAC · OWASP A01:2021 Broken Access Control CONFIRMED
Evidence
backend/app/routers/users.py:313 (update_status), :257 (update_role), :161 (bulk_action), :342 (kick_user). None checks target seniority — only self (user_id==actor.id) and _active_admin_count()<=1. The seeded non-admin Manager role holds presence.kick (seed_demo.py:56), so kick_user — which has no admin protection and no last-admin floor at all — is reachable against admins by an ordinary Manager.
Why it matters
Separation-of-duties inversion: a mid-tier operator can lock out or sign out the entire admin team down to the single surviving admin. It is not self-escalation, but it is the precondition that (with FND-003) drives active admins to zero.
Fix direction
Add a target-seniority guard to update_status / update_role / bulk_action / kick_user: a non-admin actor may not act on a target whose effective permissions aren't a subset of the actor's (and never on an admin-role target). Keep the existing count guard as a backstop.

FND-003 MEDIUM Last-admin protection is a non-locking check-then-act (TOCTOU)

Domain
Correctness / RBAC · CWE-367 TOCTOU CONFIRMED
Evidence
backend/app/routers/users.py:47 _active_admin_count is a plain SELECT COUNT(*) with no FOR UPDATE. Each guard reads the count then mutates a different row (update_status :324→:326, update_role :276→:278, bulk :192→:195). Sync endpoints run in the threadpool on separate connections at InnoDB REPEATABLE READ, so two concurrent deactivations of two distinct admins both observe count==2, both pass <=1, both commit → 0 admins. Per-item safety inside a single /bulk call (re-count each iteration) does not extend across concurrent requests.
Why it matters
The only defense against a permanent, self-inflicted admin lockout can be defeated by two well-timed requests; recovery needs direct DB access. Latent at local scale, bites under any concurrency.
Fix direction
Make count-and-mutate atomic: SELECT … FOR UPDATE the admin rows in the same transaction, or a single conditional UPDATE … WHERE (SELECT COUNT admins)>1 checking rowcount. A partial unique index / trigger asserting ≥1 active admin is a defense-in-depth backstop.

FND-004 MEDIUM A roles.manage delegate can rewrite or delete custom roles more privileged than themselves

Domain
Security: Privilege / RBAC · OWASP A01
Evidence
backend/app/routers/roles.py:140 (update_role) / :175 (delete_role). _guard_grantable only checks the new permission set is a subset of the actor's — it does not consider the role's current privilege. A non-admin roles.manage holder can strip a high-privilege custom role down to fewer/empty permissions (mass-revoking from every holder) or delete any unused custom role, regardless of how privileged it is.
Why it matters
Destructive, org-wide access change by an actor who doesn't hold those permissions — a separation-of-duties gap on the RBAC admin surface.
Fix direction
Require the actor to hold (be a superset of) the role's existing permission set before allowing edit/delete of a non-system role, in addition to the grant-subset check on the new set.

FND-005 MEDIUM Nobody — not even an admin — can attach a runtime-created custom permission to a role

Domain
Correctness / RBAC (functional defect)
Evidence
backend/app/routers/roles.py:62 _guard_grantable computes extra = keys − actor.permission_keys and 403s if non-empty, with no admin bypass (unlike users.py:303 which has if not _is_admin(actor)). An admin's permission_keys is only their role's built-ins ∪ direct grants; a freshly-created custom permission is attached to no role, so it is not in any admin's set — and attaching it via create_role/update_role 403s. The docstring's assumption ("a full admin holds every permission") is false for custom permissions.
Why it matters
Breaks the product's advertised core workflow ("admins create new permissions and roles and assign them"). A custom permission can be created but never wired to a role through the API.
Fix direction
Add the same if not _is_admin(actor) bypass to _guard_grantable that set_user_permissions already uses, and add a test that an admin can create-then-attach a custom permission.

FND-006 MEDIUM signup_mode="closed" blocks the ADMIN_EMAILS bootstrap → recovery lockout

Domain
Correctness: business logic CONFIRMED
Evidence
backend/app/auth/service.py:113 raises SIGNUP_CLOSED before the admin-bootstrap block (:116). A first-login identity listed in ADMIN_EMAILS is rejected when signup is closed, even though it is a trusted, provider-verified identity meant to seed/recover administration.
Why it matters
Inverts the trusted-identity semantics: the one path meant to guarantee an admin can always get in is the one closed mode blocks. Combined with FND-007/FND-003 it forms a family of lockout footguns.
Fix direction
Evaluate _admin_bootstrap(ident) before the closed-mode gate, so a configured admin email provisions regardless of signup mode.

FND-007 MEDIUM Both OAuth providers can be disabled, locking everyone out of authentication

Domain
Correctness: business logic
Evidence
backend/app/routers/settings.py:35 (update_settings) accepts allow_google=false and allow_microsoft=false together with no invariant. With both off, every non-dev login path 403s at service.py:70 — including admins (dev login is local-only).
Why it matters
A single settings save can make the app unauthenticatable; recovery requires DB access or a local dev-login environment.
Fix direction
Reject a settings update that would leave zero enabled providers (validate the resulting state, not just the delta).

FND-008 MEDIUM Microsoft admin bootstrap trusts an unverified, mutable email/UPN claim

Domain
Security: Authentication · OWASP A07:2021
Evidence
backend/app/auth/microsoft.py:47 derives email from email or preferred_username with no verification flag (Google enforces email_verified; Microsoft has no equivalent here). service.py:46 then bootstraps admin if that email is in ADMIN_EMAILS and the tenant matches. preferred_username/UPN is tenant-mutable.
Why it matters
Admin provisioning keys on a claim the identity provider does not assert as verified. Exploitability is gated by control of a matching UPN inside your admin tenant (a high bar), but it's a trust-boundary weakness on the most privileged path.
Fix direction
Bootstrap admin on the immutable oid (allowlist of object-ids) rather than an email claim, or require an explicit verified-email signal.

FND-009 MEDIUM Per-IP rate-limit & audit source-IP collapse to the proxy container IP

Domain
Security: abuse resistance / observability CONFIRMED
Evidence
backend/app/main.py:73 keys buckets on request.client.host (socket peer), and request_logging.py:29 deliberately ignores X-Forwarded-For. In the compose topology the browser hits the Vite/web container which proxies /api to api:8000 (vite.config.ts:32), so every API request's socket peer is the web container's IP. All users share one rate-limit bucket and one logged IP.
Why it matters
The strict login limiter and the audit trail's source IP — both advertised protections — are effectively neutralized in the shipped local topology (one user's flood throttles everyone; the log can't attribute source).
Fix direction
Terminate client traffic at a trusted proxy and enable Starlette's ProxyHeadersMiddleware with an explicit trusted-hosts list so request.client.host reflects the real client; document the requirement. (Keep XFF distrust for untrusted ingress.)

FND-010 MEDIUM Interactive API docs & full OpenAPI schema are public to anonymous users

Domain
Error handling / info disclosure · OWASP A05:2021 Misconfiguration
Evidence
backend/app/main.py:16 sets docs_url="/api/docs" and openapi_url="/api/openapi.json" with no auth; request_logging.py:12 also excludes them from the audit log.
Why it matters
For an access-control console, the full route/permission map is handed to any anonymous visitor and isn't recorded. No data leak, but it widens reconnaissance and contradicts the app's own tight posture.
Fix direction
Gate docs/openapi behind auth (or disable in non-local), or at minimum behind a permission; remove them from the audit-skip list if kept.

FND-011 MEDIUM Session IPs & user-agents exposed to any users.read holder

Domain
Security: session & privacy CONFIRMED
Evidence
backend/app/routers/users.py:362 list_user_sessions is gated on users.read and returns every row's ip + user_agent (schemas/auth.py:33 SessionOut). The app deliberately gates GPS behind the stricter users.manage/self, but a coarser location signal (IP) + device fingerprint is exposed to the broader users.read audience.
Why it matters
Inconsistent privacy model — the same directory role that is denied precise GPS is handed per-device IPs and UA strings for every user.
Fix direction
Gate other users' session IP/UA behind users.manage (or self), matching the GPS rule; or mask the IP for users.read-only viewers.

FND-012 MEDIUM GPS-derived location & timezone bypass the include_location privacy control

Domain
Security: session & privacy CONFIRMED
Evidence
backend/app/routers/auth.py:136 writes the raw GPS into last_latitude/longitude and reverse-geocodes it into user.location / user.timezone (:144-147). UserOut.from_user strips lat/long when include_location=False (schemas/user.py:82) but location/timezone are always serialized — and included in CSV export.
Why it matters
The city/region derived from opt-in GPS leaks to every users.read viewer and the CSV even though the precise coordinates are correctly gated — a partial defeat of the app's own location-privacy model. (Note: users can also self-edit these fields, so they aren't purely GPS-derived; the leak is still real when GPS populated them.)
Fix direction
Either treat GPS-derived location/timezone as location-sensitive (gate them with the same include_location rule) or store the derived label separately from the user-editable field.

FND-013 MEDIUM Synchronous per-request audit INSERT + redundant JWT decode, into an unbounded table

Domain
Performance & scalability CONFIRMED
Evidence
backend/app/main.py:51 runs record_request on nearly every response; request_logging.py:47 opens a fresh session, re-decodes the JWT (already decoded in get_current_user), and commits an INSERT. Combined with _touch's presence write (deps.py:63) that's up to two DB writes per request. request_logs has no retention/pruning and its indexes don't cover the log-viewer's actual filters (logs.py:24).
Why it matters
Write amplification on the hot path and an append-only table that grows without bound — a latent operational time-bomb and a steady per-request cost.
Fix direction
Batch/async the audit write (queue + background flush), reuse the already-decoded principal, add a retention job (or partition), and index request_logs for its real query shape.

FND-014 MEDIUM Unbounded CSV export & uncapped analytics endpoint

Domain
Performance / DoS CONFIRMED (CSV)
Evidence
backend/app/routers/users.py:113 export_users_csv materializes the entire filtered user set into memory with no limit/offset (unlike the paginated list). dashboard.py:36 /dashboard/analytics runs four aggregate scans and is only protected by the loose 600/min global bucket.
Why it matters
One users.read holder can force a full-table load or hammer the aggregate queries, saturating the single DB — no per-endpoint cost control.
Fix direction
Stream the CSV (server-side cursor / chunked rows) with a hard row ceiling; add a tighter per-user throttle or short cache to the analytics endpoint.

FND-015 MEDIUM No index on users.last_seen_at — online-count full-scans every dashboard load

Domain
Performance & scalability
Evidence
backend/app/models/user.py:38 declares last_seen_at with no index; dashboard.py:29 and :81, plus users.py:80 (online filter) and presence.py:19, all filter/COUNT on last_seen_at >= cutoff.
Why it matters
Every dashboard/presence read scans the users table; cost grows linearly with the directory and the dashboard is the landing page.
Fix direction
Add an index on last_seen_at (and consider a composite with is_active) via a migration.

FND-016 MEDIUM WebSocket presence handler runs sync DB queries on the event loop and doesn't throttle frames

Domain
Correctness & reliability CONFIRMED
Evidence
backend/app/routers/ws.py:110 — presence_ws is async but calls synchronous SessionLocal / db.get / active_session directly (connect :112, and every ≤30s re-auth :136) with no run_in_threadpool. Each query blocks the worker's single event loop; :133 reads frames with no rate limit, so a client can also spam frames to force re-auth churn.
Why it matters
Top reliability risk: a slow query or a chatty/malicious client stalls all concurrent HTTP + WS work on that worker. Latent at local scale, acute under load or with 2 workers.
Fix direction
Offload the DB work with run_in_threadpool (or an async driver), and rate-limit inbound frames / cap re-auth frequency.

FND-017 MEDIUM bulk_action commit-time DB errors escape the handler as a 500 with silent partial application

Domain
Correctness & reliability
Evidence
backend/app/routers/users.py:184-213 loops committing per item inside try/except ApiError only. A db.commit() that raises OperationalError (deadlock / lock-wait) or IntegrityError is not caught, aborting the batch with a 500 after some items already committed — and the response never reports which.
Why it matters
Non-atomic bulk operation with an unreported partial state on infrastructure errors; the operator can't tell what applied.
Fix direction
Catch SQLAlchemyError per item (rollback + record a failed result) alongside ApiError, so the batch always returns a complete per-id outcome.

FND-018 MEDIUM WebSocket presence has no connection cap and leaks dead connections

Domain
WebSocket & presence integrity
Evidence
backend/app/routers/ws.py:39 — PresenceHub appends every connection to an unbounded list with no per-user or global cap; it also bypasses the rate-limit/audit middleware (WS upgrades aren't /api-limited). Half-open connections are only pruned on a failed send during broadcast (:59), so idle dead sockets linger.
Why it matters
An authenticated client can open many connections to grow memory/roster unbounded; no backpressure.
Fix direction
Cap connections per user and globally; add a periodic ping/idle-reaper; count WS upgrades against a limiter.

FND-019 MEDIUM Migration 0002 downgrade can truncate/fail on long custom role names

Domain
Data & persistence · migration reversibility
Evidence
backend/alembic/versions/0002_rbac_presence_kick.py converts the users.role String(20) column into the RBAC role FK on upgrade; the downgrade writes role names back into a String(20). Role names allow up to 50 chars (models/role.py:23), so a longer custom role name truncates or errors on downgrade.
Why it matters
A reversible-migration guarantee that silently corrupts data for a realistic input; only bites on downgrade, but that's exactly when you least want surprises.
Fix direction
Downgrade should map unknown/over-length role names to a safe default (e.g. "user") or widen the restored column; document that custom roles don't round-trip.

FND-020 MEDIUM Vulnerable backend packages on the auth/crypto boundary; no lockfile or hashes

Domain
Dependencies & supply chain · OWASP A06 tool-backed (pip-audit)
Evidence
pip-audit on backend/requirements.txt: PyJWT 2.10.1 (signs the session JWT) → PYSEC-2026-120/175-179 (fix 2.13.0); cryptography 44.0.2 → PYSEC-2026-35/2141 + GHSA-537c-gmf6-5ccf; requests 2.32.3 → PYSEC-2026-1872/2275; starlette 0.46.2 (FastAPI core) → 7 advisories. Direct deps are version-pinned but there is no lockfile / hash pinning, so the transitive closure (incl. Starlette) floats.
Why it matters
Known advisories sit on the token-verification trust boundary; without a lockfile builds aren't reproducible and transitive drift is invisible.
Fix direction
Patch to fixed versions, adopt a hash-pinned lock (pip-compile / uv), and add pip-audit to CI. See fix-packs/FND-020.

FND-021 MEDIUM SPA served with no security response headers

Domain
Frontend / Ops · OWASP A05
Evidence
frontend/nginx.conf:1-9 serves the built SPA with only try_files — no CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy. The app also loads an external Google GSI script (frontend/index.html:34) with no CSP to constrain it.
Why it matters
No clickjacking, MIME-sniffing, or script-origin defenses on the served app. (Prod edge TLS is Caddy, out of scope, but the nginx image is in scope and ships headerless.)
Fix direction
Add a hardened header block to nginx.conf (frame-deny, nosniff, referrer-policy, a CSP allowing self + accounts.google.com).

FND-022 MEDIUM CI builds no prod image and has no dependency-audit gate

Domain
Operations & deployability · supply chain
Evidence
.github/workflows/ci.yml runs lint/tests/vite build and an e2e compose (dev stages) but never builds either Dockerfile's prod stage, and runs neither npm audit nor pip-audit. This is why FND-001/FND-020 persisted unflagged.
Why it matters
The artifact that ships (prod image) is never built in CI, and known-vulnerable dependencies aren't caught.
Fix direction
Add a docker build --target prod step for both images and an npm audit/pip-audit gate (fail on High).

FND-023 MEDIUM Prod containers run as root; per-worker in-memory security state

Domain
Operations & deployability · CIS Docker
Evidence
backend/Dockerfile / frontend/Dockerfile have no USER directive (all stages run as root). The backend prod stage hardcodes --workers 2 (backend/Dockerfile:24), but the rate-limiter (ratelimit.py), replay guard (replay.py), and presence hub (ws.py:26) are per-process — so limits double, replay isn't shared, and the presence roster splits across workers.
Why it matters
Root containers widen blast radius; and the shipped 2-worker config silently weakens three security/consistency mechanisms that are documented as if global.
Fix direction
Add a non-root USER to both images; move rate-limit/replay/presence to shared state (Redis) or run a single worker until then, and document the constraint.

FND-024 MEDIUM Edit-user modal is not an accessible dialog

Domain
Accessibility · WCAG 2.2 — 2.4.3 Focus Order, 2.1.2 No Keyboard Trap, 4.1.2 Name/Role/Value
Evidence
frontend/src/components/UserEditModal.tsx:110 renders a plain <div class="modal"> — no role="dialog"/aria-modal, no focus trap, no Escape-to-close, no focus-on-open or focus-restore-on-close. Click-outside closes it but keyboard/SR users get no dialog semantics or focus management.
Why it matters
The primary admin editing surface is not operable by keyboard/screen-reader users to AA.
Fix direction
Add dialog role + aria-modal, trap focus within the panel, move focus in on open and restore on close, and wire Escape to onClose.

FND-025 MEDIUM WebSocket presence subsystem has zero automated tests

Domain
Testing & QA
Evidence
No test exercises backend/app/routers/ws.py (the suite covers HTTP routes; there is no test_ws*). _authenticate re-implements the full auth pipeline (decode → active/approved → epoch → session row) and the broadcast gates roster visibility on can_view — all unguarded by tests.
Why it matters
A re-implemented auth + authz path (the easiest place for the two to drift) has no regression net; FND-016/-018/-027 all live here.
Fix direction
Add WS tests: unauthenticated close (1008), revoked-mid-session severance, and roster hidden from a non-presence.view connection.

FND-026 MEDIUM No negative tests for JWT validation or the security config guards

Domain
Testing & QA
Evidence
No test asserts auth/jwt.py:27 rejects a wrong-alg / missing-claim / expired / tampered token, and the pure validators in config.py:33 (secret strength), :40 (prod secure-cookie), :63 (dev-auth gate) have no unit tests despite being trivially testable.
Why it matters
The crypto and the environment-gating guards are exactly the code whose silent regression would be catastrophic — and a green suite wouldn't catch it.
Fix direction
Add negative JWT tests and unit tests for each config validator (including that dev-auth stays off outside local).

FND-027 MEDIUM Silent sign-in failure & no WebSocket reconnect

Domain
Frontend robustness · WCAG 3.3
Evidence
frontend/src/pages/LoginPage.tsx:62 — if the external Google GSI script never loads, the retry loop simply gives up after 50 tries with no visible state; the user sees a blank sign-in area. frontend/src/presence/PresenceContext.tsx:86 — the presence WebSocket never reconnects after a drop, permanently degrading to 20s HTTP polling with no signal.
Why it matters
The first is an onboarding dead-end with no error; the second is a silent, permanent capability degradation.
Fix direction
Show an explicit error + retry when GSI fails to load; add bounded exponential-backoff reconnect to the presence socket.

How it ran

A deterministic multi-agent workflow fanned out 24 finder agents across three rounds (per-dimension → cross-cutting lenses → deep dives), steering later rounds away from already-surfaced ground. Candidates were deduplicated (73 raw → 73 unique; the dedup key was strict so near-duplicates were merged at synthesis instead) and entered a two-stage verification pipeline: an adversarial refuter (instructed to kill each finding by re-reading the code) followed by a severity calibrator. Every finding cites file:line; all objective claims are backed by tool output.

Coverage statement — what was and wasn't done

  • Fully read at source: the entire backend (app/ incl. every router, auth module, model, schema; all 10 migrations; env.py; seed_demo.py; conftest.py), the key frontend surfaces (client, auth context, guards, App routes, the admin table, the edit modal, MatrixRain, login), and the full ops surface (compose, both Dockerfiles, nginx, CI, .env.example). The dynamic app was not manually driven; the live Docker stack was used only to run the automated tooling above.
  • Verification was cut short. The adversarial refuter + severity-calibration pass completed for 15 of the ~50 candidates that reached it before the agent session hit a usage limit; the remaining refuters and the completeness-critic agent failed with that limit. Those 15 carry a CONFIRMED tag; every other finding was instead adjudicated by the reviewer against a complete independent read of the same code (the reviewer had already read the whole repo during recon). No finding was accepted on a finder's word alone, but the un-tagged findings did not receive a second independent agent's refutation — treat their severities as reviewer-calibrated rather than panel-verified.
  • The automated completeness-critic did not run (session limit). Reviewer-identified residual gaps: (a) no dynamic/manual exercise of the running app or the WebSocket under load; (b) the two large admin pages (AdminRolesPage, SettingsPage) and several components (Charts, UserProfile, SessionsPanel, AppearancePanel) were read only in part; (c) no load/perf measurement was taken — performance findings are structural, not benchmarked; (d) migrations 0003–0005, 0008, 0009 downgrades were spot-checked, not each line-verified.
  • Excluded by instruction (not reviewed): the deploy/ directory (Caddyfile, prod compose) and all AWS deployment concerns. The local docker-compose.yml, Dockerfiles, nginx, and CI were in scope. One finding (FND-040) touches an RDS cert-bundle fetch only as a hermetic-build concern, without assessing the AWS path.
