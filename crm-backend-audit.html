1. Executive summary

Sharpbill is a layered ASP.NET Core/.NET 10 application with disciplined dependency injection, Dapper/MySQL persistence, a dedicated C# migrator, server-side session validation, OIDC, RBAC, and a Docker Compose development stack. The reviewed application code has meaningful security strengths; no confirmed authentication bypass, IDOR, SQL injection, or cross-tenant bypass was found in the inspected scope. The full hosted release gate is now green. Enterprise production approval still requires an independently operated immutable audit destination and the production control-plane evidence that was explicitly excluded from this remediation.

Recommendation: Conditional hold. SB-001 and SB-005 are fixed and verified by GitHub Actions run 29879026056. Production approval still depends on SB-002 and the evidence explicitly deferred under SB-003. This is a release-readiness recommendation, not a claim that an unknown external environment lacks those controls.

Five most important risks

  1. SB-002: security events have no implemented external dispatcher or immutable off-box evidence sink.
  2. SB-003: production deployment, recovery, observability, and operational-control evidence is not available for verification.
  3. SB-004: main has no branch protection/ruleset and hosted security-alert services are disabled or not enabled.

Business impact summary

A failed required release gate means an unverified build may be deployed. The lack of independently retained security evidence weakens investigation after credential, database, or administrator compromise. Missing production evidence prevents confident statements about recovery objectives, backup safety, rollout control, and customer-data protection. Database lock hot paths and local-only coordination can degrade availability as authenticated traffic or login bursts rise.

Notable strengths

  • Fallback authentication policy, permission policies, server-side session-state validation, and service-level hierarchy checks provide defense in depth.
  • Strong local/production configuration validation rejects insecure cookies, weak secrets, broad trusted-proxy CIDRs, non-TLS production database settings, and non-local dev authentication.
  • Parameterized Dapper access, FK/check/unique constraints, bounded worker batches, transactional migrations, and documented retention/hold behavior are present.
  • Images are largely digest-pinned; the API image runs non-root; CI includes formatting, package audit, image scanning, and SBOM generation.

SB-001 — Current main cannot complete the Docker/MySQL end-to-end gate

HIGHConfirmedFIXEDConfidence: High
Category / mappings
Release engineering and database connectivity. CWE: not applicable to a standalone code vulnerability. OWASP ASVS/API Top 10: secure delivery/verification control; no direct API category.
Component and path
GitHub Actions E2E job; one-shot C# migrator against Compose MySQL.
Root cause / execution path
The E2E workflow starts MySQL then invokes migrator migrate. Local Compose disables TLS by default, while the migrator connection-string builder does not set the client option required by the MySQL caching_sha2_password failure path. The job fails before API, web, or Playwright execution.
Why it matters / scenario
A commit can be present on main without a passing full-stack migration/login/authorization test. An operator or CI runner attempting the documented local/ephemeral startup may receive the same database authentication failure.
Likelihood / impact / affected scope
Likelihood: demonstrated. Technical impact: required E2E evidence is absent. Business impact: release confidence and recovery of the verified deployment path are reduced. Affected: every release relying on this workflow.
Compensating controls
Backend, frontend, image, SBOM, and scan jobs passed in the same run; local Compose configuration parses; production configuration requires verified TLS. These do not make the skipped E2E path pass.
Recommendation / implementation outline
Centralize connection policy. Prefer verified TLS whenever practical; for the isolated non-production Compose case, explicitly permit public-key retrieval only there, never in production. Cover both API and migrator builders with the same policy and test fixture.
Proof, effort, owner, compatibility
Re-run the exact Compose migration, seed, API readiness, and Playwright job on a clean runner; add a test for local MySQL 8.4 authentication and a production-TLS negative test. Effort: small. Owner: backend + platform. No schema migration expected; coordinate only configuration rollout.
Fix action / remediation status
Fixed and hosted-verified on 2026-07-21. The API and migrator enable AllowPublicKeyRetrieval only for APP_ENV=local with TLS disabled; production keeps VerifyFull and public-key retrieval disabled. Added positive local and negative production tests. Rebuilt Docker images; local migration/validation passed, and GitHub Actions run 29879026056 completed the migration, API, web, Playwright, image, and supply-chain gates successfully.

SB-002 — Security audit evidence is not independently immutable or delivered

HIGHConfirmedConfidence: High
Category / mappings
Security logging, audit integrity, governance. CWE-778 (insufficient/incomplete logging evidence); OWASP ASVS security-logging/error-handling control family; OWASP API Top 10: operational security-misconfiguration relevance.
Component and path
Security event repository, transactional outbox primitives, hosted-worker registration, retention.
Root cause / execution path
Security events and pending delivery records are atomically stored in the same MySQL database. Claim/lease/mark primitives exist, but no hosted dispatcher sends them to a separately administered sink. Retention eventually removes expired events, including undelivered events.
Why it matters / scenario
An administrator, database compromise, destructive recovery event, or failed-but-never-dispatched outbox can leave the organization without independently retained evidence of authentication and privileged actions. The primary DB is not an immutable, independently controlled audit store.
Likelihood / impact / affected scope
Likelihood: present in the repository runnable topology. Technical impact: no nonrepudiable off-box trail. Business impact: impaired incident investigation, legal hold support, customer assurance, and change accountability. Affected: security events and privileged-action evidence.
Compensating controls
Event/outbox writes are transactional; claim/lease/retry primitives are implemented; internal security-event access is permission protected; the documentation explicitly discloses the gap rather than claiming compliance.
Recommendation / implementation outline
Deploy a least-privileged dispatcher outside the API process. Deliver signed or tamper-evident envelopes to restricted append-only/WORM storage or a SIEM, with independent credentials, dead-letter handling, lag/loss/tamper alerts, and deletion/hold policy alignment.
Proof, effort, owner, compatibility
Fault-inject sink outage, restart, duplicate delivery, database tamper attempt, and retention boundary; prove alerting and recovery without exposing event payloads. Effort: large. Owner: security/platform/data. No application API migration necessarily required; requires infrastructure, ownership, retention, and possibly legal/privacy coordination.

SB-006 — Authentication validation used exclusive-lock hot paths

MEDIUMConfirmedFIXEDConfidence: High
Category / mappings
Database concurrency and availability. CWE-400 (resource exhaustion/availability pressure). OWASP ASVS availability/resilience controls; OWASP API Top 10 2023 API4 Unrestricted Resource Consumption relevance.
Component and path
Session authentication handler, session validation service, user repository.
Root cause / execution path
For each authenticated request, the handler validates the session. The original implementation requested FOR SHARE but unconditionally upgraded the final user read and session read to FOR UPDATE, then wrote activity inside the authorization transaction. That serialized concurrent requests for the same user/session.
Why it matters / scenario
A dashboard with parallel API calls, multiple browser tabs, a mobile client retry, or an administrator editing the user concurrently can queue behind an exclusive lock. Lock waits increase latency and can amplify deadlocks or timeout failures.
Likelihood / impact / affected scope
Likelihood: direct code path; volume threshold needs load validation. Technical impact: same-user request serialization. Business impact: slow or unavailable interactive CRM use for active users. Affected: authenticated API requests and administrative user/session operations.
Compensating controls
Server-side session-state validation, transactional authorization snapshots, bounded pools, and command timeouts remain in place.
Recommendation / implementation outline
Use a consistent shared/optimistic authorization snapshot for normal validation and acquire an exclusive lock only around a proven conditional last-seen update. Preserve revocation/deactivation semantics and test stale/session-revoked behavior.
Proof, effort, owner, compatibility
Automated contract coverage verifies authorization snapshot commit precedes activity writes. A real-MySQL test proves two same-user authentication snapshots coexist and stale activity writes are throttled. Representative 50+ request load and lock-wait profiling remains a capacity-validation recommendation, not a code-fix blocker. Owner: backend/data. No schema or public API change.
Fix action / remediation status
Fixed and hosted-verified on 2026-07-21. User, role, permission, identity, and session authorization reads use compatible shared locks. The transaction commits before conditional user/session last-seen writes, eliminating shared-to-exclusive upgrades while preserving revocation/deactivation snapshot semantics. Database predicates suppress redundant activity updates during concurrent requests. GitHub Actions run 29879636621 passed all required jobs.

SB-007 — OIDC nonce issuance used global serialized lock hot paths

MEDIUMConfirmedFIXEDConfidence: High
Category / mappings
Authentication resilience and database concurrency. CWE-400. OWASP ASVS authentication/availability controls; OWASP API Top 10 2023 API4 relevance.
Component and path
Nonce service, nonce repository admission control, nonce rate limiter.
Root cause / execution path
The original implementation used a static SemaphoreSlim(1) inside each API process and then locked the singleton site_settings row FOR UPDATE, extending serialization across replicas that shared MySQL.
Why it matters / scenario
During a workforce login event, SSO outage/retry burst, or distributed abuse attempt, nonce latency can grow linearly behind the settings-row lock. Per-IP local throttling does not bound distributed source traffic or cross-replica load.
Likelihood / impact / affected scope
Likelihood: code path is direct. Technical impact: login throughput bottleneck and lock contention. Business impact: delayed access to CRM during an identity event. Affected: all OIDC login initiations.
Compensating controls
Atomic delete-on-consume replay protection, a 5,000-active-nonce ceiling, expiration pruning, and the 30/minute/IP API limiter remain in place.
Recommendation / implementation outline
Replace singleton-settings locking with a dedicated atomic quota/admission design that preserves replay resistance and capacity guarantees; use database atomic update, a distributed limiter, or an explicitly designed nonce store. Do not weaken nonce validation to remove the lock.
Proof, effort, owner, compatibility
Unit coverage proves shard encoding and that 64 shard quotas sum exactly to 5,000. A real-MySQL race test proves only one concurrent claimant can consume the final slot in a shard. The rebuilt API returned HTTP 201 with a valid nonce. Multi-instance burst/fault profiling remains recommended capacity evidence. Owner: backend/identity/data. No schema or public API change.
Fix action / remediation status
Fixed and hosted-verified on 2026-07-21. Removed the process-wide semaphore and all nonce dependence on site_settings. Cryptographically random nonces are distributed across 64 quota shards. Each shard uses a database-scoped advisory lock and short owned transaction, held through commit; callers try shards in a randomized order. Capacity remains partitioned to exactly 5,000 and consume remains an atomic delete. GitHub Actions run 29880201498 passed backend real-MySQL, E2E, and supply-chain jobs.

SB-008 — Retention and activity-telemetry health cannot be fully observed

MEDIUMConfirmedConfidence: High
Category / mappings
Observability, retention reliability, operational logging. CWE-778. OWASP ASVS security logging/error handling control family; OWASP API Top 10: no direct one-to-one category.
Component and path
Retention worker, request-log buffer worker, protected log metrics endpoint, operations/privacy policy.
Root cause / execution path
Retention emits structured count/failure logs but no application metrics for last successful cycle, oldest eligible record, backlog, hold state, or alert delivery. Request logs enter a bounded in-memory channel and intentionally drop records on saturation, persistence failure, cancellation, or shutdown.
Why it matters / scenario
A retention worker can repeatedly fail or fall behind without a machine-actionable alert. Under database outage or traffic pressure, request activity telemetry becomes incomplete. A security investigator may mistake it for a complete audit trail despite documentation classifying it only as telemetry.
Likelihood / impact / affected scope
Likelihood: drop behavior and missing metrics are direct code facts. Technical impact: delayed operational detection and incomplete activity telemetry. Business impact: prolonged privacy/retention exceptions and weaker incident reconstruction. Affected: request-log and privacy-lifecycle operations.
Compensating controls
Queue depth/drop/error counters are exposed behind authorization; batches are bounded and transactional; retention is independently committed and hold-aware; the documentation correctly warns that request logs are telemetry, not immutable audit evidence.
Recommendation / implementation outline
Emit durable metrics for each retention category (success timestamp, backlog/oldest age, hold state, failures, batch count) and configure alert ownership. Export queue metrics and structured logs to a central collector. Keep request logs explicitly non-audit; use SB-002's independent security-event sink for evidence.
Proof, effort, owner, compatibility

MEDIUMProbableConfidence: Medium

The limiter is in-memory and partitioned by remote IP. Presence connections and broadcasts are held in one process. Documentation confirms rate limits, presence, replay memory, and WebSockets are process-local and restricts the reference topology to one API replica until externalized.

Compensating controls
Forwarded headers are ignored unless explicit proxy networks are trusted; current documented reference topology is one replica; rate-limit partitions are bounded. These controls intentionally constrain, not solve, multi-replica operation.

Either enforce a documented one-replica service limit in deployment admission or externalize rate limiting, nonce/replay coordination, presence/pub-sub, and scheduled-work leadership. Prefer ingress rate limiting plus a shared coordination store and a leader/lease mechanism.

SB-011 — Large log/export and transient-lock paths lack enterprise volume proof

MEDIUMProbableConfidence: Medium
Category / mappings
Performance, reliability, resource consumption. CWE-400. OWASP ASVS availability/resilience controls; OWASP API Top 10 2023 API4 Unrestricted Resource Consumption.
Component and path
Request-log repository/listing, security-event CSV export, database transaction retry strategy.
Root cause / execution path
Request-log browsing performs a full filtered count, uses OFFSET paging, and allows leading-wildcard path search. Compensating controls
Limits are bounded; security-event metadata is capped; database pools/timeouts exist; business-service retry handles some idempotent work; retention has bounded batches. No production-shaped EXPLAIN/load/fault evidence was provided.

Use keyset pagination and optional/approximate counts for operational logs; profile and add only evidenced composite indexes; stream CSV directly with byte/concurrency limits; centralize narrowly scoped retry for idempotent MySQL lock/deadlock sections with jitter and metrics.
Proof, effort, owner, compatibility
Run EXPLAIN ANALYZE and load/failure tests on representative log volume; test concurrent max exports and injected MySQL 1205/1213 errors; record p95/p99, heap, lock, and retry outcomes. SB-012 — Client-selected request IDs weaken correlation uniqueness

LOWConfirmedFIXED LOCALLYConfidence: High
Category / mappings
Observability integrity. CWE: not applicable to an access-control defect. OWASP ASVS logging/monitoring control family; OWASP API Top 10: no direct category.
Component and path
Request-context middleware and structured request logging.
Root cause / execution path
The original request context accepted a requester-supplied X-Request-ID as the authoritative correlation identifier rather than always generating a server-controlled unique ID.
Why it matters / scenario
A client can deliberately reuse another value or choose a collision-prone value, making cross-log correlation less reliable. This does not bypass authentication or authorization; actor and source IP are also recorded.

Likelihood: direct behavior. Technical impact: ambiguous correlation. Business impact: modestly slower incident triage. Affected: logs/traces that treat this field as unique.

Structured logs include independent request context and user/source information; no sensitive body/query content is intentionally logged.
Recommendation / implementation outline
Generate a server request ID for every request. Preserve a sanitized client correlation ID in a distinct field if interoperability requires it, and document which identifier is authoritative.
Proof, effort, owner, compatibility
Integration tests send duplicate valid client headers and prove distinct 32-hex server IDs while preserving the client value separately. Invalid client values are not propagated. Owner: backend/operations. No schema migration; consumers should use response X-Request-ID as authoritative.

Fixed locally on 2026-07-21. Middleware always generates the authoritative server request ID. A valid legacy caller X-Request-ID is stored as client_request_id, tagged separately on the activity and structured request log, and echoed only as X-Client-Request-ID.
